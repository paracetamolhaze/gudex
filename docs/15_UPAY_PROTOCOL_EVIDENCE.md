## Общая отправка и разбор ответа

E1 создаёт HTTP-клиент с базой `/api/v1/card`. Методы передают объект тела непосредственно в `post`; финансовые endpoint-адреса ниже относительны к этой базе.

В E9, функция `Wb`, наблюдаются:

- JSON-сериализация через `JSON.stringify` для обычных запросов.
- Заголовки `Token`, `deviceID`, `pretreatment`, `DateTime`, `language`, `Accept-Language`, `X-B3-Traceid`, `X-B3-Spanid`.
- Успех ответа: `code === 200` **или** одновременно `code === 0` и `success === true`; результат метода — поле `data`.
- Коды `10020`, `10011`, `10021` приводят к удалению сохранённого `brokerToken` и переходу на вход.
- Остальные ответы отклоняются с `msg`/`message`. Такое клиентское отклонение само по себе не доказывает отсутствие финансового эффекта на сервере.

Trace/span ID создаются из текущего времени. В исследованном interceptor нет специального заголовка идемпотентности; trace ID нельзя считать таким ключом.

## Выпуск: POST `/applyOpenCard`

E1: метод `fastCardApply`. E2: функция `ls`, вызов `Gt`, обработчик `onSetCodeVal` компонента платёжного PIN.

Предварительные чтения в интерфейсе:

1. `GET /getMayApplyCardDetail`, query `agentCardId`.
2. `GET /getCardFee`, query `agentCardId`, `customerNo`.
3. `GET /get/kyc` и `GET /get/kycStatus`, query `customerNo`, `agentCardId`.

Тело построено из **глубокой копии текущей формы**, поверх которой записываются поля:

| Поле | Статически наблюдаемое значение |
|---|---|
| `amount` | `(defaultOpenAmount + openFee) * number`; вычисляется через Decimal из данных `/getMayApplyCardDetail` |
| `number` | В исследованном компоненте вычисляемое значение `1` |
| `agentCardId` | ID продукта из маршрута интерфейса |
| `holdBackPath`, `holdFrontPath`, `holdPassportPath`, `signPath` | URI первого загруженного файла либо пустая строка |
| `pinCode` | Зашифрованный платёжный PIN из E5 |

Форма сначала содержит поля `customerNo`, `givenName`, `lastName`, `email`, `phone`, `globalCode`, `phoneCountryCode`, `documentType`, `annualIncome`, `company`, `position`, `profession`, `workYear`, `selfie`, `addressType`, `recipientAddressId`, поля документов/подписи и служебные поля интерфейса. После `/getCardFee` она заменяется данными ответа с преобразованиями файлов, `documentType = defaultType`, `copyPhone`, `copyEmail` и нормализацией `workYear`.

Поэтому **полный и минимально обязательный набор полей выпуска из публичного кода не установлен**: он зависит от ответа `/getCardFee`, `needParams`, типа продукта и результатов KYC. Поля `selfie` и URI остальных документов не следует считать взаимозаменяемыми.

После разрешения Promise интерфейс игнорирует тело результата и переходит на `/card-manage/recharge-records`. Сопоставление ответа с `partnerCardId`, `last4`, датой окончания или ID заявки в этом обработчике отсутствует. Успешный HTTP-ответ не доказывает готовность карты.

## Пополнение: POST `/recharge`

E1: `cardRecharge`; E3: функция `Z`, вызов `Y`.

Наблюдаемое тело состоит из `pinCode` (шифротекст), `agentCustomerCardId` (ID выбранной карты) и `amount` (значение формы). `field3`, используемое для расчётного зачисления, в запрос не включается: клиент выбирает из формы только `amount`.

Перед отправкой UI получает `GET /getRechargeCardInfo?agentCustomerCardId=…`. Для отображения и проверки суммы используются `minRechargeAmount`, `maxRechargeAmount`, `rechargeRate`, `executeExchangeRate`, `walletAssetInfo.virtualBalance`; расчётное зачисление — `amount * (100 - rechargeRate) / 100 * executeExchangeRate` с округлением вниз до двух знаков.

Это свидетельство, что `amount` — вводимая сумма списания до вычета комиссии; валюта, точный тип JSON-поля и окончательный серверный расчёт должны быть подтверждены реальным контрактом. Нельзя напрямую подставлять GUDEX `netUsd` вместо суммы списания.

Результат мутации не разбирается: UI показывает успешное уведомление и закрывает drawer. ID заказа/операции, стадия исполнения и сверка итоговой суммы здесь не извлекаются.

## Шифрование платёжного PIN

Это отдельный шестизначный пароль UPay, не четырёхзначный PIN GUDEX и не TOTP.

- E5 принимает шесть непустых цифровых символов, вызывает экспорт `e` из E6 и передаёт его результат как `setCodeVal`.
- E7 получает `userInfo` через `GET /api/v1/sys/member/loginInfo` (путь подтверждается E8).
- E7 вычисляет строку ключа как MD5 от конкатенации `userInfo.id` и `broker-manage`; IV берётся из `userInfo.iv`.
- **Несмотря на имя `aes_128_cbc`, E6 использует WebCrypto `AES-GCM`, не CBC.** Ключ и IV преобразуются в байты кодами символов строки; hex-строка MD5 не декодируется в 16 байт. Обычный MD5 hex даёт 32 ASCII-байта ключа.
- Открытый PIN кодируется UTF-8 через `TextEncoder`; результат `crypto.subtle.encrypt` передаётся в Base64. `additionalData` и явный `tagLength` не заданы. Не следует добавлять CBC padding или отдельно преобразовывать hex IV без подтверждения.

Для расшифровки реквизитов E1 применяет другой ключ: MD5 от `accountCardId + broker-manage`, с IV из того же user store; поля `cardNumber`, `cvv`, `expirationTime`. Это статическая схема, успешная расшифровка реальных реквизитов в этой проверке не подтверждена.

## Идемпотентность и границы доказательств

В явных payload-полях выпуска, пополнения и freeze/unfreeze не обнаружены `externalRef`, GUDEX operation ID, `idempotencyKey` или иной гарантированный клиентский ключ. Это **не доказывает**, что сервер таких механизмов не поддерживает: неизвестны backend-валидация, дополнительные поля динамической формы и ответ мутации.

Для безопасного включения финансового адаптера ещё необходимо установить:

1. Поддерживаемый сервером уникальный внешний reference либо другой однозначный способ сопоставить GUDEX-операцию с заявкой/проводкой UPay после потери ответа.
2. Реальные ответы трёх мутаций: ID операции, признаки принятия/завершения, конечный статус и возможность запросить этот результат без повторной мутации.
3. Точный обязательный KYC/документный payload для выбранного продукта, валюта суммы и фактические списания/комиссии.
4. Поведение при timeout, истечении сессии, асинхронной обработке и параллельной отправке; доказанное отсутствие операции перед возвратом резерва.

До этого `findCardByExternalRef`/`isRechargeDone` нельзя заменять догадками по последней карте, балансу или близким времени/сумме. Финансовые вызовы GUDEX должны оставаться заблокированными, а неопределённый исход — сохранять резерв и требовать сверки.

### Наблюдение после одобрения: статус клиента и квитанция фотографий

Последующие чтения16:31–16:45UTC показали selectedIDitemstatus1, authResult1 и primaryApprovedNum1. При этом native `nationalityCode`, `frontPhoto`, `backPhoto` имеют явный null. Диагностика путей и алиасов страны не участвует в решении об одобрении.

При такой форме ответа нужно различать подтверждение статуса конкретного клиента у UPay и совпадение квитанции конкретных фотографий. Положительный статус выбранного native item подтверждает первое; null не подтверждает второе. Исходные хеши нельзя заменять или объявлять совпавшими. Отдельная политика `issuer_subject_status` должна требовать точной текущей user/customer/SID-привязки, принятого POST с `accepted_envelope`/`post_dispatched`, подтверждённых загрузок, зафиксированного допустимого состояния до отправки2/4 и последующего review3, затем текущих selecteditem1/authResult1/productlevel1 и совпавшего certifiedtype/номера клиента. Все3 native документных поля должны присутствовать и быть именно null; неизвестный POST, чужая связь, mixed/non-null несовпадение, старый journal и advanced product остаются закрыты.

В журнале это отдельное основание `approvalBasis=issuer_subject_status`, `photoReceiptMatched=false`; прямое совпадение документов обозначается `document_hashes`/true. Такое одобрение не является утверждением, что получены обратно и сверены именно новые фотографии. Для текущей отправки состояния4→ACK→3 наблюдались root в доверенных ответах OPS до добавления новых stage-полей; узкая operator attestation может записать только эти наблюдения с текущими SID/requestHash и новым временем фиксации, без повторного POST и без прямого изменения approved. Последующее обычное чтение должно самостоятельно подтвердить текущий положительный статус. Для новых анкет этапы сохраняются во время обработки; точное время банковского решения не выводится из часов нашего запроса.

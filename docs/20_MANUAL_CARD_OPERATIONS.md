# Ручная проверка и выпуск карт

`CARD_ISSUANCE_MODE=manual` переводит новые анкеты и выпуски в очередь операторов GUDEX. `ADMIN_TELEGRAM_IDS` содержит числовые Telegram ID администраторов через запятую. Вход в админку — через Telegram Mini App и код-пароль GUDEX; общий `OPS_API_TOKEN` браузеру не передаётся.

## Путь клиента

1. **Анкета.** Клиент заполняет одну анкету: личные данные, телефон, документ с фото, адрес для карты (страна из собственного списка ISO). `POST /v1/card-application` сохраняет анкету `pending/manual_review` и адрес. Если баланса уже хватает на выпуск, стоимость резервируется сразу; иначе анкета ждёт оплату (админ её ещё не видит).
2. **Оплата на кошелёк приложения.** Пул адресов: `APP_WALLET_TRON` и `APP_WALLET_EVM` (через запятую, по 5 кошельков; ключи у владельца, у сервера только адреса). Клиент выбирает сеть, и ему на `FEE_ADDRESS_LEASE_MINUTES` (60) закрепляется свободный адрес — плательщика определяет адрес, сумма обычная (10 USDT/USDC). После окончания закрепления адрес «отдыхает» `FEE_ADDRESS_COOLDOWN_MINUTES` (60): поздний перевод в это время засчитывается последнему клиенту. Все адреса заняты — клиент видит «попробуйте через несколько минут».
3. **Проверка только пока ждём.** Сервер читает TronGrid и публичные RPC (BNB Chain, Ethereum, Polygon) только по закреплённым адресам и только пока есть открытые закрепления или идёт «отдых» адреса; в остальное время в блокчейн ничего не отправляется. Пока клиент смотрит экран оплаты, проверка идёт каждые ~10 секунд, иначе раз в минуту (cron).
4. **Оплата пришла.** Сумма зачисляется на баланс клиента; если хватает на выпуск — стоимость резервируется, анкета уходит админам (уведомление), клиент получает «Оплата получена. Ожидайте проверку данных — специалист выпускает вашу карту». Не хватает — клиент получает, сколько дослать на тот же адрес. Перевод без закрепления — в админке «Платежи на кошелёк приложения», оператор зачисляет вручную.
5. Оператор создаёт клиента и карту в UPay (пополнение 0), в админке вводит Customer ID и реквизиты карты (номер, срок, CVV — для показа клиенту). Бот находит новую активную карту в списке карт этого Customer ID. В одной транзакции анкета одобряется, реквизиты сохраняются зашифрованными, карта активируется, резерв проводится. Клиент получает «Карта •• 1234 выпущена».
6. «Отклонить заявку» с причиной: анкета `rejected`, фото удаляются, резерв возвращается на баланс.

## Что делает бот UPay

Только по Customer ID: `GET /card/list` (баланс и состояние карт клиента), `POST /card/getPageToTransaction` (покупки по карте), `POST /card/thawFrozen` (заморозка и разморозка по нажатию клиента, сразу), `GET /sys/member/loginInfo` (данные для шифрования платёжного PIN и вход). Любой другой запрос отклоняется до отправки. Покупки показываются в Mini App (история и уведомление внутри приложения), сообщения в Telegram о покупках не отправляются. Пополнение карты в ручном режиме выключено — оно появится вместе с личным кошельком клиента.

Создание карты в UPay остаётся действием оператора. Кнопка привязки GUDEX сама не создаёт карту и не списывает дополнительные средства у провайдера. Перед ручным выпуском оператор обязан проверить оплату и действующую заявку. Эта схема не меняет личность клиента, не подставляет другие паспорта или контакты и не отменяет ограничения карточного продукта.

## Доступ и данные

- Откройте Mini App под аккаунтом из `ADMIN_TELEGRAM_IDS`: **Профиль → Админка GUDEX** либо кнопка в уведомлении. Поиск принимает точный Telegram ID или внутренний UUID GUDEX.
- Все `/v1/admin/*` требуют разблокированную пользовательскую сессию и проверяют список администраторов на сервере. Изменения дополнительно требуют двухминутный confirmation token существующего `/security/confirm`.
- Фото открываются только по отдельному запросу администратора, не попадают в Telegram и клиентский кэш. Срок временного хранения задаёт `KYC_DOCUMENT_TTL_SECONDS` (по умолчанию 24 часа). Если фото истекли, оператор отклоняет анкету с просьбой загрузить документы заново.
- Фото конкретной заявки недоступны через ID другой анкеты. Сведения о просмотре/решении/привязке записываются в `admin_audit_log`.
- В уведомлениях администраторам только ID клиента и этап. Постоянный outbox разделяет отправку каждому получателю; повторное сохранение не создаёт повторное событие. При потере ответа Telegram после принятой отправки возможен повтор сообщения с тем же ID заявки.
- Полные PAN/CVV, документы и OTP не вводятся в форму привязки и не хранятся в её DTO. Данные карты для клиента продолжает получать существующий защищённый маршрут реквизитов.

## Старые операции и смена режима

Старые операции `unknown` и операции с попыткой отправки не превращаются в новый ручной выпуск, не повторяются и не возвращают резерв по факту пустого списка карт. Они видны администраторам для отдельной сверки по точному результату исходной операции.

Задача автоматического выпуска, которая ещё строго `pending`, имеет `attempts=0`, не имеет журнала UPay и связана с пустой ожидающей картой, может перейти в ручную очередь без нового резерва. Перенос происходит под блокировкой операции. Ограничение БД запрещает ручным операциям переходить к отправке или увеличивать число попыток. Ручной режим сохраняется у операции даже при последующем включении автоматического режима.

Автоматическая KYC-задача, остановленная сменой режима, требует отдельного разбора; факт остановки не означает одобрение или отказ эмитента. Уже отправленная или неизвестная KYC-заявка не отправляется повторно.

Пополнения, заморозка, история и депозиты сохраняют прежние интеграционные настройки; переключатель ручного выпуска не является переключателем всех финансовых операций.

# GUDEX

Исходный код GUDEX: [приватный репозиторий GitHub](https://github.com/paracetamolhaze/gudex).

Актуальное состояние и правила продолжения работы — `CLAUDE.md` и `docs/14_IMPLEMENTATION_STATUS.md`. Протокол UPay с источниками — `docs/15_UPAY_PROTOCOL_EVIDENCE.md`.

## Идея
GUDEX — мобильное приложение с крипто-балансом и виртуальной/физической картой, где пользователь пополняет баланс криптовалютой (в первую очередь USDT/USDC), выпускает карту и оплачивает обычные покупки через карточную инфраструктуру партнёра.

Пользователь не видит broker-admin и не работает с ним напрямую. Все операции с карточной партнёркой проходят через наш backend.

## Базовый пользовательский сценарий
1. Пользователь регистрируется в приложении.
2. Проходит необходимые проверки/KYC.
3. Пополняет крипто-баланс.
4. Подаёт заявку на карту внутри приложения.
5. Наш backend автоматически создаёт заявку/карту в партнёрской панели.
6. Карта появляется в приложении.
7. Пользователь пополняет карточный баланс/использует доступный баланс — в зависимости от логики партнёра.
8. Покупки проходят через Visa/card infrastructure, а крипто-конвертация происходит под капотом.

## Главный принцип
Для пользователя GUDEX должен ощущаться как обычное современное финансовое приложение, а не как сложная криптобиржа.

## Код

GUDEX — **Telegram Mini App**: пользователь открывает бота и нажимает «GUDEX». Всё работает на Vercel.

```
apps/miniapp    Mini App: React + Vite, RU/EN, тёмная тема
apps/api        backend: Node.js + Fastify + PostgreSQL (Drizzle); на Vercel — одна serverless-функция
packages/shared общие типы API, справочник валют, работа с суммами
scripts/        сборка для Vercel (Build Output API)
archive/        прежняя версия-приложение на Expo (не используется)
```

Реализован настоящий адаптер UPay: вход/TOTP, KYC с фотографиями, выпуск, пополнение, блокировка и реквизиты карты. Production использует UPay, отдельную live-БД и выключенный деморежим. Пополнение кошелька до первой карты реализовано через отдельный счёт UPay; индивидуальный адрес продавца не выдаётся за личный адрес клиента. Payment Password проверен. Реальную оплату и выпуск в клиентском тесте подтверждает сам владелец. Актуальные результаты публикации и ограничения — в [документе 14](docs/14_IMPLEMENTATION_STATUS.md), полный маршрут и правила зачисления — в [документе 16](docs/16_LIVE_MINIAPP_READINESS.md).

Демо-депозиты имеют только непереводимые идентификаторы `GUDEX-DEMO:…`. Для настоящих счетов нужны `CARD_PARTNER=upay`, `DEV_TOOLS=false`, `UPAY_INVOICE_DEPOSITS_ENABLED=true`, доступы бота с правом Deposit и чистая БД с live-меткой. Выключение создания счетов сохраняет сверку ранее выставленных. Вывод криптовалюты отключён. Демонстрационный баланс нельзя отправить в UPay.

### Вход и безопасность
- **Вход через Telegram:** Mini App отправляет подписанные Telegram данные (`initData`), сервер проверяет подпись токеном бота. Регистрации нет — аккаунт создаётся при первом открытии.
- **Код-пароль проверяется на сервере.** Пока он не введён, сессия «заблокирована»: деньги и карты недоступны. 5 ошибок — блок на 15 минут.
- **Face ID / Touch ID / отпечаток** — через биометрию Telegram: на устройстве хранится токен, который отдаётся только после биометрии.
- **Реквизиты карты** — только с отдельным подтверждением кодом или биометрией (токен на 2 минуты).
- Ключи авторизации GUDEX выводятся из `TELEGRAM_BOT_TOKEN`. UPay использует отдельные `UPAY_LOGIN`, `UPAY_PASSWORD`, `UPAY_TOTP_SECRET`; операторские команды защищены `OPS_API_TOKEN`, cron — `CRON_SECRET`. Смена PIN отзывает старые сессии и биометрию.

### Как устроены деньги
- **Леджер с двойной записью** (`apps/api/src/ledger/ledger.ts`): каждое движение — сбалансированная транзакция, баланс нельзя увести в минус, повтор события не проводится дважды.
- **Операции с картой асинхронные:** резерв и задача создаются в одной транзакции. На production Vercel PRO защищённый cron запускается каждую минуту; автоматический tick и завершение sync-job проверены. Есть ограниченные проходы после пользовательских запросов и `npm run api:worker` для другого хостинга. OPS показывает heartbeat и состояние очереди.
- **Неизвестный исход:** `unknown` сохраняет резерв. Операторская сверка только читает результат партнёра; повтор отправки и автоматический возврат запрещены до подтверждённого исхода.
- **Идемпотентность:** приложение шлёт `idempotencyKey`, адаптер сохраняет журнал перед единственной отправкой. Результат ищется по точному заказу/ID карты; если UPay потерял квитанцию, операция требует операторской сверки. По времени и сумме совпадения не выбираются.
- **Уведомления** о зачислениях, выпуске, пополнении и покупках приходят сообщениями от бота.
- Тарифы GUDEX — переменные окружения. Реальные расходы UPay учитываются отдельно; реферальное вознаграждение начисляется только из оставшейся маржи.
- Демо-справочник сетей не доказывает поддержку live-пополнений. Для отдельных счетов проверены USDT TRC20/BEP20 и USDC BEP20; интерфейс получает текущие сети, лимиты и точность из нативного каталога. Зачисление требует точной успешной квитанции с фактической суммой, а не возврата со страницы оплаты.

### Запуск для разработки

Нужны Docker, Node 24 и доступ к приватному репозиторию.

```bash
git clone https://github.com/paracetamolhaze/gudex.git
cd gudex
npm ci
npm run db:up
cp apps/api/.env.example apps/api/.env   # DEV_LOGIN=true — вход без Telegram
npm run api:dev                           # API на :4100, миграции применяются сами
npm run miniapp:dev                       # Mini App на http://localhost:5174
```

Вне Telegram (в браузере) локально включается тестовый вход `DEV_LOGIN`. На Vercel он запрещён.

В тестовом режиме есть кнопки «Симулировать пополнение» и «Симулировать покупку». KYC с фамилией `REJECT` отклоняется — для проверки сценария отказа.

### Деплой на Vercel

```powershell
$env:GUDEX_CRON_SCHEDULE='* * * * *'; npm run vercel:build # production: минутный cron
npx vercel deploy --prebuilt --prod           # загружает готовую сборку
```

Переменные окружения: `DATABASE_URL` (Neon), `TELEGRAM_BOT_TOKEN`, `DEV_TOOLS=true` и `CARD_PARTNER=mock` для демо. Дополнительная конфигурация описана в `apps/api/.env.example` и `docs/14_IMPLEMENTATION_STATUS.md`. `POST /v1/telegram/setup` теперь требует операторский bearer token.

На этой Windows-машине `node scripts/vercel-upay-release.mjs` развёртывает проверенный `.vercel/output`, создаёт недостающие операторский/cron секреты в Vercel и выполняет только вход/чтение UPay. Локальные копии новых служебных секретов защищены Windows DPAPI в `%LOCALAPPDATA%/GUDEX`; значения не печатаются. Результат проверки сохраняется в `.vercel/last-upay-check.json`. Скрипт меняет production и запускается после всех проверок.

### Тесты

```bash
npm run api:test      # деньги, карты, KYC, вход через Telegram, код-пароль, бот (нужна база)
npm run api:test:unit # протокол UPay и HTTP-клиент Mini App, без базы и настоящего UPay
npm run typecheck
```

`api:test` сбрасывает схемы отдельной тестовой БД. Проверяйте `TEST_DATABASE_URL` и никогда не направляйте тесты на production.
